## 0. The scheduling rule — read this before anything else

> **Deploy a trivial slice to production at roughly HOUR 2, before the app is finished.**

Not at hour 7. Not "once it works locally". At hour 2, when the only thing that exists is a
login page skeleton and a health route.

**Why.** `00-foundation.md` §9 lists **R2** (Prisma + Neon + Vercel wiring) as a known risk.
Everything in R2 fails *at deploy time only*: `prisma generate` being skipped by dependency
caching, the pooled-vs-direct connection string mix-up, Node version drift, a missing env
var, an Edge/Node runtime mismatch. None of it can be caught locally, because locally you
have a `node_modules` you generated by hand and a `.env` that is always present. The hour-2
deploy converts an unknown-unknown into a 20-minute known problem with six hours of runway
behind it.

**The first deploy is a checkpoint, not a finish line.** Its job is to answer four yes/no
questions, and nothing else:

| Question | Answered by |
|---|---|
| Does the Next.js build succeed on Vercel with pnpm? | build log is green |
| Did `prisma generate` actually run in the Vercel build? | no "Module not found: @prisma/client" |
| Can a serverless function reach Neon over the **pooled** URL? | `/api/health` returns `db: "up"` |
| Did the migration actually land in the production database? | `/api/health` returns a `users` count ≥ 3 |
| **Can a logged-out stranger reach the app at all?** | the production URL loads in an **incognito window** with no Vercel SSO wall — see §4a step 7b |

That fifth question is not optional and it is not obvious: **Vercel Deployment Protection** is
invisible to you, because you are signed in. A protected deployment answers every one of the other
four questions perfectly and shows the reviewer a login wall, which zeroes C14 with no symptom you
would ever see. Two minutes, at hour 2.

If all four are green at hour 2, the rest of the day is product work. If any is red, you fix
it while it is still cheap.

### The trivial slice, concretely

Ship exactly this — it is ~15 lines and it stays in the final product:

```ts
// app/api/health/route.ts
import { NextResponse } from "next/server";
import { prisma } from "@/lib/db";

export const runtime = "nodejs";        // Prisma cannot run on Edge
export const dynamic = "force-dynamic"; // never prerender a DB read at build time

export async function GET() {
  try {
    const users = await prisma.user.count();
    return NextResponse.json({ ok: true, db: "up", users });
  } catch (e) {
    return NextResponse.json(
      { ok: false, db: "down", message: (e as Error).message },
      { status: 503 },
    );
  }
}
```

It exposes a row count and nothing else — no emails, no ids. That is an acceptable amount of
information to leak from a demo app, and it is worth it for a one-request answer to "is
production alive".

### 2.2 Copy BOTH connection strings

Neon's connection widget shows **one** string at a time with a toggle between the pooled and
the direct (unpooled) variant. Labels in the console change over time; **the label is not the
identifier — the hostname is.**

> **The pooled host contains the literal substring `-pooler`. The direct host does not.**
> That is the only test you need. Apply it to every string you paste, every time.

Copy both into a scratch buffer:

```text
# POOLED  → goes to DATABASE_URL   (note "-pooler" in the host)
postgresql://neondb_owner:npg_EXAMPLEpassword@ep-cool-frog-a1b2c3d4-pooler.us-east-1.aws.neon.tech/neondb?sslmode=require

# DIRECT  → goes to DIRECT_URL     (same host, no "-pooler")
postgresql://neondb_owner:npg_EXAMPLEpassword@ep-cool-frog-a1b2c3d4.us-east-1.aws.neon.tech/neondb?sslmode=require
```

### 2.3 Which is which, and why

| | `DATABASE_URL` | `DIRECT_URL` |
|---|---|---|
| Neon string | **pooled** (`-pooler` in host) | **direct** / unpooled |
| Behind | PgBouncer, transaction pooling mode | the Postgres instance itself |
| Used by | **runtime** — every Prisma query from a Vercel serverless function | **`prisma migrate` / `prisma db push` only** |
| Prisma field | `datasource.url` | `datasource.directUrl` |
| Why | Each serverless invocation is a fresh process wanting its own connection. Neon's free tier caps direct connections in the low hundreds; a pooler multiplexes thousands of clients onto a few real backends. | Migrations need a **session**-scoped connection: Prisma takes a Postgres **advisory lock** to serialise concurrent migrators, and transaction-mode pooling does not preserve session state. |

**Add the query parameters.** Both strings keep `?sslmode=require` — Neon refuses plaintext
connections, and without it you get a TLS error rather than a helpful message. The pooled
string additionally gets `pgbouncer=true`, which tells Prisma to stop using named prepared
statements (PgBouncer in transaction mode reuses backends between statements, so a named
prepared statement created on one request is missing on the next). Final values:

```text
DATABASE_URL="postgresql://…-pooler.us-east-1.aws.neon.tech/neondb?sslmode=require&pgbouncer=true&connect_timeout=15"
DIRECT_URL="postgresql://…us-east-1.aws.neon.tech/neondb?sslmode=require"
```

If Neon hands you a string that also carries `channel_binding=require`, keep it; if and only
if you hit a driver error naming channel binding, drop that one parameter (see §8).

### 2.4 Failure mode if you swap them

This is the single highest-value paragraph in this document, because **one of the two swaps
does not fail immediately**.

| Swap | What happens | When you find out |
|---|---|---|
| `DIRECT_URL` gets the **pooled** string | `prisma migrate deploy` hangs and then dies with `Timed out trying to acquire a postgres advisory lock` (or applies a migration and then wedges). The pooler cannot hold the session-level lock Prisma needs. | Immediately — loud and obvious. Annoying, not dangerous. |
| `DATABASE_URL` gets the **direct** string | **Everything works.** Local dev works. The build works. Your smoke test with one browser tab works. Then a reviewer opens the app, autosave fires a few PATCHes, Vercel spins up several concurrent function instances, and you get `FATAL: too many connections for role "neondb_owner"` / `Can't reach database server`. | During the reviewer's session. This is the dangerous one. |

So: **check the `-pooler` substring on `DATABASE_URL` before every deploy.** It costs three
seconds and it is the failure that a passing smoke test cannot catch.

## 3. Environment variables

Three variables. That is the whole surface — no analytics keys, no blob tokens, no OAuth
credentials, because `00-foundation.md` §4 cut all of it.

| Variable | Purpose | Local (`.env`) | Vercel — which environments | Example value |
|---|---|---|---|---|
| `DATABASE_URL` | Runtime Prisma connection. Read by `datasource.url`. Must be the **pooled** Neon string. | ✅ (local Postgres or the same Neon DB) | **Production + Preview + Development** | `postgresql://neondb_owner:npg_xxx@ep-cool-frog-a1b2c3d4-pooler.us-east-1.aws.neon.tech/neondb?sslmode=require&pgbouncer=true&connect_timeout=15` |
| `DIRECT_URL` | Migrations only. Read by `datasource.directUrl`. Must be the **direct** Neon string. | ✅ | **Production + Preview + Development** — it is never used at runtime, but Prisma's schema validation wants it defined, and a missing env var referenced by the schema fails the build. | `postgresql://neondb_owner:npg_xxx@ep-cool-frog-a1b2c3d4.us-east-1.aws.neon.tech/neondb?sslmode=require` |
| `AUTH_SECRET` | HS256 signing key for the `jose` session JWT (`00-foundation.md` §2). Used by the login route and the Edge middleware. | ✅ (any local value) | **Production + Preview + Development** | `9tS0m8b0y0hQxA0m0Yy0m0dV0nJ0kR0pP0lZ0aQ0xY0=` |

Notes that matter:

- **Generate `AUTH_SECRET` with:**
  ```bash
  openssl rand -base64 32
  ```
  32 bytes of entropy, base64-encoded. Do not reuse a value from another project, do not
  hand-type one, and do not commit the output anywhere.
- **Local and production `AUTH_SECRET` should differ.** They are independent signing keys.
- **Rotating `AUTH_SECRET` in production invalidates every existing session cookie.** Users
  land back on `/login`. That is correct behaviour, not a bug — but do not rotate it at hour
  7:50 while the reviewer link is already in the Drive folder.
- Vercel's **Development** environment values are only consumed by `vercel env pull`. Your
  local `.env` remains the source of truth for `pnpm dev`.
- **Set every variable for Preview as well as Production.** A variable scoped to Production
  only produces a green build and a 500 on every preview URL — a confusing 20 minutes.

### `.env` vs `.env.example`

- **`.env` is gitignored.** It holds real credentials. `.gitignore` must contain `.env` and
  `.env*.local` (Next.js's default `.gitignore` already does; verify, don't assume).
- **`.env.example` is committed.** It documents the contract for the reviewer following the
  README's local-setup steps. It contains no secrets:

```dotenv
# .env.example — copy to .env and fill in. Never commit .env.
# Pooled Neon connection (host contains "-pooler"). Used at runtime.
DATABASE_URL="postgresql://USER:PASSWORD@HOST-pooler.REGION.aws.neon.tech/neondb?sslmode=require&pgbouncer=true&connect_timeout=15"
# Direct Neon connection (no "-pooler"). Used ONLY by `prisma migrate`.
DIRECT_URL="postgresql://USER:PASSWORD@HOST.REGION.aws.neon.tech/neondb?sslmode=require"
# Session JWT signing key. Generate with: openssl rand -base64 32
AUTH_SECRET="replace-me"
```

## 5. Build configuration

### 5.1 `package.json` — the parts that affect deployment

```jsonc
{
  "name": "shared-docs",
  "private": true,
  "engines": { "node": "22.x" },
  "packageManager": "pnpm@10.34.3",
  "scripts": {
    "dev": "next dev",
    "build": "prisma generate && next build",
    "start": "next start",
    "postinstall": "prisma generate",
    "db:migrate": "prisma migrate dev",
    "db:deploy": "prisma migrate deploy",
    "db:seed": "prisma db seed",
    "test:unit": "vitest run --project unit",
    "test": "vitest run"
  }
}
```

**`package.json` is written once, in full, by `01-data-and-persistence.md` §2** — the block above is
the deployment-relevant subset, not a competing definition. Two things in it changed:

- **`build` is `prisma generate && next build`, not bare `next build`.** `01` §2's argument wins and
  it costs three seconds: `postinstall` is skipped when Vercel restores a cached `node_modules`, and
  the resulting failure — `Module not found: Can't resolve '@prisma/client'` — is a row in this
  runbook's own §8 troubleshooting table. Belt *and* braces, deliberately.
- **VOID — D006. There IS a `prisma.seed` key and it is correct.** The paragraph below assumed the
  Prisma 7.10.0 pin; we are on **6.19.3**, where `package.json#prisma.seed` works and
  `prisma.config.ts` must not exist. Original text: ~~`00-foundation.md` §2a pins Prisma **7.10.0**, which moved seed
  registration into `prisma.config.ts`. A `prisma.seed` block in `package.json` is silently ignored
  on 7.x, which means `pnpm prisma db seed` does nothing and `migrate reset` stops re-seeding.

Note also that `test` runs **both** Vitest projects and therefore needs Docker; the reviewer entry
point is `test:unit`, which needs nothing (`06-test-plan.md` §2.4).

### 5.2 Why `postinstall: "prisma generate"` is mandatory

`@prisma/client` is a *generated* package: the installed module is a stub until
`prisma generate` writes the typed client from `prisma/schema.prisma`. Two things on Vercel
conspire to skip that generation:

1. **Vercel caches `node_modules` between builds.** On a cache hit, the package manager's
   install is a no-op — and so is any generation that would have been triggered by installing
   `@prisma/client`. Your build then compiles against a stale (or empty) client. The classic
   shape of this bug: the *first* deploy is green, and the *second* one fails, or worse,
   silently ships a client that does not know about a column you added.
2. **pnpm 10 does not run dependency lifecycle scripts by default.** `@prisma/client`'s own
   `postinstall` is blocked unless the package is allow-listed under
   `pnpm.onlyBuiltDependencies`. Under pnpm 10 the dependency's script is not a fallback you
   can rely on at all.

A root-level `postinstall` belongs to *our* package, so it runs on every install regardless
of both issues. It is idempotent, it costs a few seconds, and it is the single most common
cause of the "Module not found: `@prisma/client`" Vercel failure. **Do not remove it.**

### 5.3 Build command, and the deliberate absence of migrations

| Setting | Value |
|---|---|
| Install command | *(default)* `pnpm install` |
| Build command | *(default — reads `package.json`)* `prisma generate && next build` |
| Output directory | *(default)* `.next` |
| Node.js version | `22.x` (pinned twice: `engines` + Vercel project setting) |

Leave the build-command **override** off in the Vercel UI; the value comes from `package.json`, so
there is one place to change it.

> **Decision: we do NOT run `prisma migrate deploy` in the Vercel build.**
> The build command generates the client and builds the app, and nothing else. Migrations are run
> **by hand from the developer machine against `DIRECT_URL`** (§6, step 5).

Reasoning:

- **A failed migration should not be entangled with a build.** If `build` is
  `prisma migrate deploy && next build`, a bad migration turns into a red build, and the
  Vercel log mixes SQL errors into webpack output. Worse, a migration can fail *after*
  partially applying — leaving the database in a state that the previous deployment (still
  serving traffic) does not expect. Separating them means a failed migration is a failed
  migration, in a terminal, with `prisma migrate status` available to inspect it.
- **Concurrent builds racing migrations is a real hazard.** Vercel builds Preview and
  Production deployments in parallel, and a quick succession of pushes queues several builds
  at once. All of them would run `migrate deploy` against the *same* Neon database
  simultaneously. Prisma's advisory lock means the losers block until they time out — the
  observable symptom is builds that randomly take four minutes and then fail with a lock
  timeout. Since Preview and Production share one database here (§2.1), this is not
  theoretical.
- **The build environment is the wrong place for a direct connection.** Runtime should only
  ever hold the pooled URL. Keeping migrations on the developer machine keeps the blast
  radius of `DIRECT_URL` down to one laptop.

The cost is one manual command per schema change. Over an 8-hour project with maybe three
migrations, that is ~30 seconds of typing in exchange for removing a whole class of hour-7
failure. Take the trade.

### 5.4 `prisma/schema.prisma` datasource

Exactly as locked in `00-foundation.md` §9/R2:

```prisma
datasource db {
  provider  = "postgresql"
  url       = env("DATABASE_URL")   // pooled  — runtime
  directUrl = env("DIRECT_URL")     // direct  — migrations only
}

generator client {
  provider = "prisma-client-js"
}
```

The model definitions are canonical in `00-foundation.md` §5 and are not restated here.

### 5.5 Runtime rules that only bite in production

- Any route touching Prisma declares `export const runtime = "nodejs"`. Prisma cannot run on
  the Edge runtime.
- **The Edge middleware must never import Prisma or `bcryptjs`.** It verifies the `jose` JWT
  and nothing else — that is exactly why `00-foundation.md` chose `jose` over a Node-only
  library. See `03-auth-and-permissions.md`.
- Route handlers that read the session or the database declare
  `export const dynamic = "force-dynamic"`, so Next does not try to prerender them at build
  time (a build-time DB read is a build-time failure).

## 8. Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `git push` fails: `Permission denied (publickey)`, `could not read Username for 'https://github.com'`, or `gh` erroring on `ssh` | The remote was switched to SSH, or the credential helper was dropped. The `gh` on this machine is **snap-confined and cannot `exec ssh`**, so SSH is not an option here (`DECISIONS.md` D004) | Put the remote back on HTTPS and restore the helper: `git remote set-url origin https://github.com/TheNatas/shared-docs.git` then `git config --local credential.helper '!gh auth git-credential'`. Re-run `gh auth status` if it still fails. On the dashboard path the push *is* the deploy trigger, so this blocks the hour-2 deploy gate — fix it before anything else. |
| `PrismaClientInitializationError` in Vercel runtime logs | `DATABASE_URL` missing for the environment being served (set for Production only, hitting a Preview URL), or wrong/expired Neon password, or missing `sslmode=require` | `vercel env ls` — confirm the var exists for **both** Production and Preview. Re-copy the string from Neon. Redeploy (env changes need a new deployment). |
| `Module not found: Can't resolve '@prisma/client'` at build | `prisma generate` never ran — missing root `postinstall`, or a cached `node_modules` skipped it | Restore **both** `"postinstall": "prisma generate"` and `"build": "prisma generate && next build"` (§5.1–5.2) — the second exists precisely because the first can be skipped. Then in Vercel: **Deployments → ⋯ → Redeploy** with **"Use existing Build Cache" unticked**. |
| The production URL shows a **Vercel login / SSO wall** to anyone who is not you | Deployment Protection is enabled for Production | Settings → Deployment Protection → disable for Production, then **verify from a logged-out incognito window**. Invisible to you otherwise (§0, §4a step 7b). |
| `pnpm prisma db seed` prints nothing and inserts no rows | **On the 6.19.3 pin (D006) this row does not apply** — `package.json#prisma.seed` is present and works. If it fires anyway, the key was deleted. | Restore `"prisma": { "seed": "tsx prisma/seed.ts" }` in `package.json`. Do **not** add `prisma.config.ts` — that is a Prisma 7 concept and 6.19.3 ignores it. |
| Build log: *"Ignored build scripts: … Run pnpm approve-builds"* | pnpm 10 blocking dependency lifecycle scripts | Usually harmless because our root `postinstall` handles Prisma. If a native dep genuinely needs it, add `"pnpm": { "onlyBuiltDependencies": ["prisma", "@prisma/client", "esbuild"] }` to `package.json`. |
| `FATAL: too many connections for role "neondb_owner"` / `Can't reach database server` under light load | `DATABASE_URL` is the **direct** string, not the pooled one — the classic swap (§2.4). Or `PrismaClient` is being constructed per request instead of via a module singleton. | Put the `-pooler` string in `DATABASE_URL`, keep `pgbouncer=true`, redeploy. Confirm `lib/db.ts` uses the `globalThis` singleton pattern. |
| `prepared statement "s0" already exists` | Pooled connection without `pgbouncer=true` | Append `&pgbouncer=true` to `DATABASE_URL`, redeploy. |
| Error mentioning **channel binding** / SCRAM | `channel_binding=require` in the string, unsupported by the driver path in use | Remove only that parameter; keep `sslmode=require`. |
| Build/runtime error: *"The edge runtime does not support Node.js 'crypto'/'fs' module"* (or similar) | Something Node-only reached the Edge runtime — usually `middleware.ts` importing Prisma, `bcryptjs`, or a module that transitively imports `lib/db.ts` | Middleware imports **only** `jose` + `next/server`. Move any DB work into a Route Handler with `export const runtime = "nodejs"`. See `03-auth-and-permissions.md`. |
| Infinite redirect loop (`ERR_TOO_MANY_REDIRECTS`) on `/login` | The middleware `matcher` covers `/login` (or `/api/auth/*`, or static assets), so an unauthenticated user is redirected to a page that redirects again. Or the middleware reads a cookie name the login route does not set. | Restrict the matcher to `['/documents/:path*']` plus an explicit exclusion of `_next`, static files and `/api/auth`. Assert the cookie name is one exported constant used by both sides. |
| Login returns `200` but the next request is unauthenticated (works locally, fails in production) | Cookie rejected by the browser: `secure: true` served over http, an explicit `domain` that does not match `*.vercel.app`, or `sameSite: "strict"` dropping it on a redirect | Set exactly: `httpOnly: true, sameSite: "lax", path: "/", secure: process.env.NODE_ENV === "production"`, and **never set `domain`**. Verify in DevTools → Application → Cookies that the cookie exists for the vercel.app host. Ensure the login `fetch` uses a **relative** URL (same-origin) so the `Set-Cookie` is stored. |
| `migrate deploy` says *"No pending migrations to apply"* but the app 500s with "relation does not exist" | (a) `prisma/migrations/` was never committed, so there is nothing to apply; (b) you migrated database A and the app points at database B; (c) `prisma db push` was used earlier, so `_prisma_migrations` disagrees with reality | `git ls-files prisma/migrations` — if empty, `git add -f prisma/migrations && git commit`. Print the host of both `DATABASE_URL` and `DIRECT_URL` and confirm they are the *same* Neon endpoint. Last resort on a throwaway demo DB: `prisma migrate reset` against `DIRECT_URL`, then re-seed. |
| Seed ran against the wrong database (local data gone, or prod unexpectedly reset) | A stale `.env` / `.env.production.local` was in scope when `db seed` ran | Not recoverable — there is no backup on the free tier (§10). Re-run the seed against the **correct** database and move on. Prevention: always run the `echo "$DATABASE_URL" | sed …` host check from §6 step 6 first. |
| Deploy is green, `/api/health` is green, but `/documents` 500s | Env var scoped to the wrong Vercel environment, or a route missing `export const dynamic = "force-dynamic"` and being prerendered at build | Check `vercel logs <url>` for the actual stack. Fix scope or add the export. |
| Build fails on a TypeScript or ESLint error that `pnpm dev` never showed | `next dev` does not type-check the whole project; `next build` does | Run `pnpm build` **locally** before every push after the freeze. Do **not** "fix" it with `typescript.ignoreBuildErrors` — a reviewer reads `next.config.ts`. |

## 9. Rollback

**Promote a previous deployment (dashboard).**

1. Vercel → project → **Deployments** tab.
2. Find the last deployment marked **Ready** that you know passed the smoke test (§7). The
   commit message column is why commit messages are worth writing.
3. **⋯** menu → **Promote to Production** (Vercel also surfaces this as **Instant Rollback**
   from the current production deployment's page).
4. Confirm. It is a traffic switch onto an already-built artifact, so it takes seconds, not a
   rebuild.
5. Re-run the smoke test against the production URL.

**CLI equivalent:**

```bash
vercel ls                       # find the target deployment URL
vercel promote <deployment-url> # or: vercel rollback
```

**The caveat that matters: rollback moves code, not the database.**

Vercel has no idea your schema changed. If deployment N added a required column and you roll
back to N-1, the old code queries a table that now has a column it never writes to — fine if
the column is nullable or defaulted, a hard failure if it is `NOT NULL` without a default.
The reverse is worse: a rolled-back *migration* would drop columns that live data uses.

**Therefore: prefer additive migrations for the whole assessment.**

| Do | Don't |
|---|---|
| Add new columns as nullable, or with a default | Add `NOT NULL` without a default to a populated table |
| Add new tables and indexes freely | Rename a column in place (that is a drop + add) |
| Widen a type | Narrow a type, or drop a column |
| Get the schema right **before** the hour-2 deploy | Restructure the schema after the freeze |

If a genuinely breaking schema change is unavoidable, do it in this order: migrate the
database first, then deploy the code — and accept that rollback past that point is off the
table. With ~8 hours and three seeded users, the correct answer is nearly always: don't.

## 10. Production readiness we deliberately skipped

Say this out loud in the video and repeat it in `ARCHITECTURE.md`. Naming what you skipped —
and what you would do instead — is the graded skill (`00-foundation.md` §4).

| Skipped | Why it is right to skip here | What we would do with real time |
|---|---|---|
| **Custom domain** | `*.vercel.app` is public, HTTPS, and instantly testable. A domain adds DNS propagation risk on the day and buys the reviewer nothing. | Add the domain in Vercel → Settings → Domains, two DNS records. |
| **Monitoring / alerting** | Nobody is on call for a 3-user demo. An uptime integration is 20 minutes that buys zero reviewer-visible value. | Sentry for exceptions, a healthcheck ping against `/api/health`, alerts to Slack. |
| **Structured logging** | Vercel's per-function logs are enough to debug a deploy in the moment. Adding pino + a log drain is infrastructure with no consumer. | Request-scoped JSON logs with a correlation id, shipped to a drain, tied to the error envelope's `code`. |
| **Backups beyond Neon defaults** | Neon's free tier retains a short PITR window; the entire dataset is reproducible from `prisma db seed` in five seconds. There is nothing here worth protecting. | Longer PITR retention, plus a nightly `pg_dump` to object storage. |
| **Rate limiting** | No public signup, three seeded accounts, unlisted URL. The realistic threat is zero. | Upstash/Vercel KV token bucket on `/api/auth/login` and the import route, keyed by IP + email. |
| **Staging environment** | A second Neon database and a second Vercel project doubles the env-var surface — precisely the surface that R2 says is most likely to break. Vercel Preview deployments already give per-PR URLs. | A Neon branch per preview deployment, wired via the Neon–Vercel integration, seeded automatically. |

Two more, stated for honesty: **no per-preview database isolation** (Preview and Production
share one Neon database, §2.1), and **no CI gate on the deploy** — tests are run locally with
`pnpm test` before pushing rather than as a required GitHub Actions check. With an 8-hour
budget, a red CI run that blocks a deploy at hour 7 is a bigger risk than the bug it catches.

## Rulings and remaining open questions

Items 2–5 were proposals and are now written into `00-foundation.md`. **Nothing in this runbook is
still open.** The one item that was — the Neon region — is ruled in `DECISIONS.md` D003.

- ✅ **Pooled-URL query parameters are part of R2**: `?sslmode=require&pgbouncer=true` plus a
  connection limit on the pooled string. Without `pgbouncer=true` you get intermittent
  `prepared statement "s0" already exists` errors that read as random flakiness.
- ✅ **The nested-repo step is explicit**: `git init` inside `shared-docs`, and `shared-docs/` added
  to the parent `.gitignore` (§6 step 1). Vercel cannot import a directory that is not its own repo.
- ✅ **Preview and Production share one Neon database.** A deliberate simplification (§10); it means
  a preview deploy can mutate the data a reviewer sees.
- ✅ **`/api/health` is in the API table** (`00-foundation.md` §7) and in `02-api-contract.md` §13 as
  a `withPublic` route. Session-free by design, returns `{ok, db, users}` — a row count, no PII.
- ✅ **Deployment Protection is now R2b in `00-foundation.md` §9**, checked at the hour-2 deploy from
  an incognito window. It was previously proposed only in `09-video-and-submission.md` and owned by
  nobody, which made it the highest-consequence unowned item in the set.
- ✅ **Neon region is DECIDED: AWS `us-east-1`, paired with Vercel `iad1`** (`DECISIONS.md` D003).
  Not a default and no longer a question. Reviewers are US-based and Neon's free tier has no
  South America region, so location was never really in play. The region is fixed at project
  creation, so it is settled before §2.1 runs — and the Vercel function region is **explicitly
  set** to `iad1` in §4a step 7 (or §4b's note) rather than assumed. Record the region in the
  README (Definition of done) and in `00-foundation.md` §2.
- ✅ **The repo exists, is public, and is already pushed** — `github.com/TheNatas/shared-docs`,
  spec set as commit 1, implementation from commit 2 (`DECISIONS.md` D004). §4a's "Import Git
  Repository" path therefore runs as written. The remote is **HTTPS** with
  `credential.helper = !gh auth git-credential`, because the snap-confined `gh` on this machine
  cannot `exec ssh` (§6 step 2; failure mode in §8).

2. **Pooled URL parameters are a refinement of R2.** `00-foundation.md` §9/R2 says the
   datasource declares `url` (pooled) and `directUrl` (unpooled) but does not mention query
   parameters. This spec requires `?sslmode=require&pgbouncer=true&connect_timeout=15` on the
   pooled string; without `pgbouncer=true` you get intermittent
   `prepared statement "s0" already exists` errors that look like random flakiness. Proposed
   as an addition to R2, not a contradiction.
3. **The nested-repo step is a deployment prerequisite that foundation only implies.**
   §2 says the repo lives inside `~/Documents/natas` and "never `git add` it from the
   parent". Deployment additionally requires `git init` inside `shared-docs` and a

4. **Preview and Production share one Neon database.** Foundation does not address preview
   environments. This is a deliberate simplification (§10) and it means a preview deployment
   can mutate the data reviewers see. Acceptable for a demo; flagging it so it is a decision
   rather than an accident.
5. **`/api/health` is a new route not listed in `00-foundation.md` §7's API table.** It is
   session-free by design (it must be callable by `curl` and by an uptime check) and returns
   only `{ ok, db, users }` — a row count, no PII. Proposed as a one-line addition to the API
   table.
