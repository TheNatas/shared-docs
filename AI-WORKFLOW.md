# AI workflow note

This project was built with heavy AI assistance: the specification set, most of the implementation and the tests
were generated by Claude agents working in parallel. The brief evaluates *"practical AI usage, not
volume of AI usage"* — so the headline is that **nothing here is asserted because a model said
it.** Every claim below has a command behind it, and where the model was confidently wrong it is
named in [`specs/DECISIONS.md`](./specs/DECISIONS.md) rather than quietly fixed.

---

## 1. Which AI tools I used

| Tool / model | What it did |
|---|---|
| **Claude Opus 5 in Claude Code**, multi-agent | Produced `specs/` **before any code existed** — 14 documents, ~11,600 lines, by 13 parallel subagents against a hand-written `00-foundation.md` locked first. That is commit 1; implementation starts at commit 2 |
| Same, as implementation agents | Waves of 3–11 concurrent agents on disjoint file sets. The largest ran eleven at once: nine API routes, the import pipeline and the whole UI |
| Same, as adversarial critics | Two critics against the spec set, plus a verifier that re-audited it after an amendment and found 8 real defects |
| `npm view` against the registry | Not AI — the tool used to *check* the model's version claims, since its training data predates much of what `package.json` pins |

**Not AI-assisted:** the Neon and Vercel setup, the production credentials, the walkthrough video,
and the rulings in `specs/DECISIONS.md` — that file is mine and no delegated agent writes to it.

## 2. Where AI materially sped up the work

**Parallel implementation against a frozen contract.** The largest saving by far. Eleven agents
built the backend and the frontend *simultaneously*, because nothing in the UI depended on a route
*body* — only on the API contract frozen in `lib/api-types.ts` a wave earlier. That parallelism is
only available if the contract exists first, which is what the specs bought.

**Adversarial review before a line of code.** The consistency critic found **six of nine specs
contradicting a sibling** — error codes, capability names, the Zod major version, module paths, env
var names. Each becomes a real bug the moment parallel agents build from disagreeing documents.

**Exhaustive test matrices.** `lib/permissions.test.ts` is 4 roles × 6 capabilities = 24 explicit
cells transcribed from the foundation spec; the integration suite is 45 cases. Enumerating a matrix
is exactly the tedium a model is good at, and the output is checkable against the spec it came from.

## 3. What AI-generated output I changed or rejected

The easiest section to fake, so every row names an artifact a reviewer can open.

| # | What AI produced | Why it was wrong | What shipped |
|---|---|---|---|
| 1 | Both Prisma halves pinned to **7.10.0** (a registry check had flagged `prisma@latest` as an `8.0.0-rc`) | `postinstall` failed on the first `pnpm install`. | 4 | Three modules reaching for three different Zod APIs — `required_error` (v3) in `lib/env.ts`, a `zod/v4` subpath import in `lib/documents/content.ts`, bare-v4 syntax pending in a third | A pin taken from one spec's open-questions note instead of the canonical `00-foundation.md`. | 5 | `.env.production.local` as the filename for the Neon credentials | A **Next.js convention name**, loaded ahead of `.env` in production mode — not an inert label | **Rejected.** Renamed to `ops/neon.env`, which no framework auto-loads, with the reason spelled out in `.gitignore` (D013) |

### The one that passed its tests

Row 5 did not look like a failure. A "local" end-to-end smoke run against `PORT=3111 pnpm start`
**wrote to the production database** — `pnpm start` is `next start`, which runs in production mode,
and Next.js loads `.env.production.local` first. Four junk documents and a share reached Neon, and
the suite passed **31/31** against it. Nothing errored. What caught it was a later check asserting
an exact row count (`alice owned=4`, got `8`); a liveness check — `db: "up"` — would have passed
happily. Production was restored to exactly `{ users: 3, docs: 5, shares: 4 }`, and this is the
direct reason the integration suite carries the guard described in §4.

### Where agents overrode their own briefs, and were right

Twice I handed an agent an instruction that contradicted the specs and it refused. The share agent
was briefed that revoking a nonexistent share returns `404`; it implemented **idempotent `200`**,
citing four spec locations and a graded test case that double-revokes — my brief carried a
pre-reversal design. The validation agent was told to reject a 60-deep nesting chain; it refused,
because four spec locations had already deleted that bound, and shipped the root-shape guard and
1 MB byte ceiling that actually exist — *a test asserting a limit the implementation does not have
is worse than no test.* An agent that reports a contradiction beats one that produces a green diff.

## 4. How I verified correctness, UX quality and implementation reliability

**Correctness — 169 automated tests.** 124 unit (~0.5s; no database, no network, no `.env`) and 45
integration (~3.1s against a real Postgres in Docker). Three checks are worth naming, because each
was established by removal or comparison rather than asserted:

| Property | How it was established |
|---|---|
| The unit suite genuinely needs no environment | `.env`, `.env.test` and the production credentials file were physically moved aside and the vars unset; it still ran green |
| No-access is indistinguishable from nonexistent | The integration case asserts the no-access body **deep-equals the nonexistent-id body** — the two responses are compared to *each other*, not to a literal, because that equality *is* the anti-enumeration property |
| The truncating suite can never reach a real database | `tests/integration/global-setup.ts` parses `TEST_DATABASE_URL` with `new URL()` and compares database, port and host exactly — a substring check accepts `…/production?application_name=shared_docs_test`. Five wrong URLs were fed to it and **all five exited 1**, including the near-miss `shared_docs_dev`, whose row counts were unchanged before and after |

Alongside those: `tsc --noEmit` clean, `pnpm build` green across 15 routes, and a 31-check end-to-end
smoke of the access-control surface against a running server — byte-identical `401`s for
wrong-password versus unknown-email, `404`-not-`403`, the role matrix, the stale-token `409`, and the
import accept/reject cases. One bug this style caught: at the first deploy `/api/health` returned
`users: 0` — the migration had reached Neon but the seed had only ever run against local Postgres.
The gate asserted `users: 3` rather than `db: "up"`, which is the only reason it surfaced before the
demo.

**UX quality.** There is no automated browser coverage. That is the one real omission, it is named
as such in `specs/06-test-plan.md` §6, and it is the first thing I would build with more time.

What *was* done: the deployed UI was driven with Playwright to confirm the screens actually render
and the controls actually exist — the demo-account buttons, the dashboard's two sections, the
editor toolbar's `aria-label`s and keyboard-shortcut titles, the import control's `accept` list and
its limits copy, and the share dialog's fields. That pass earned its keep immediately: it found that
`ShareDialog` had been **built but never mounted**, so the app had no Share button at all. The API
tests were green throughout, because the share *routes* were correct — an API suite structurally
cannot see an unmounted component. One line fixed it.

A 24-step manual checklist (`specs/06-test-plan.md` §9) defines the rest of the pass — two
side-by-side browsers, Alice in a normal window and Carol in a private one so the cookie jars are
genuinely separate, covering the read-only banner, a not-found page rather than a permission-denied
page, a devtools `PATCH` returning `403` while the toolbar is hidden, the conflict banner and its
**Reload**, and the inline error for a rejected file type. It is the procedure of record; it has not
been run end-to-end by hand, and I am not claiming otherwise.

**Reliability.** The app was deployed at hour 2, not hour 7, precisely so a failure would be cheap —
and the gate earned it immediately by catching the missing seed above. It also asserts that
Deployment Protection is off, because an SSO wall looks perfectly healthy to the owner and blocks
every reviewer. The Neon pooled/direct split was proven with **12 simultaneous queries**, since a
single sequential query succeeds against either endpoint — which is how a swapped pair looks healthy
until a reviewer's concurrency arrives. Not done, and not claimed: load testing, error monitoring,
uptime alerting, and CI — the suites run locally.
